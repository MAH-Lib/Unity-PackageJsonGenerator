# 要求内容：フェーズ 4 機能の追加（#7〜#12）

> 作業ディレクトリ：`.steering/20261021-phase4-features/` ／ 作成日：2026-10-21 ／ ステータス：承認済み
> 対象：開発環境 Unity 6000.3.26f1
> 関連する永続的ドキュメント：`Docs/functional-design.md`（§2〜§7 の該当箇所、§8 は新しい既知の問題があれば追加）、`README.md` / `README.ja.md`、`CHANGELOG.md`。いずれもステップごとに、そのステップの分を更新する

## 0. 進め方

フェーズ 4 の 6 つの機能を、この 1 組の文書（requirements / design / tasklist）で扱う。実装は下のステップの順に 1 つずつ行う。各ステップでは、実装 → ドキュメントの更新（functional-design.md・CHANGELOG・README）→ 配布フォルダへの同期まで行い、Unity での確認手順を示して止まる。ユーザーの確認が済み、指示があってから次のステップに進む。コミットは指示があったときに、ステップ（機能）ごとに分ける（各コミットにその機能のコードとドキュメントがそろうようにするため）。

| ステップ | 機能 | 計画書の番号 |
|---|---|---|
| 1 | 英語・日本語の切り替え | #7 |
| 2 | プレビュー版のバージョン | #8 |
| 3 | ライセンス None と LICENSE.md の作成 | #9 |
| 4 | 読み込んだパッケージの記憶 | #10 |
| 5 | 未対応キーの保持と JSON プレビュー | #11 |
| 6 | 現在の Unity の反映と Create 前の確認 | #12 |

順番の理由：ステップ 1 で文言を 1 か所の表にまとめておくと、ステップ 2 以降で増える文言を最初から両方の言語で書ける。ステップ 4 の記憶は入力状態の全体を保存するので、ステップ 2・5 で入力状態に項目を足し終えてから行うほうが手戻りが少ないが、ステップ 5 の「未対応キー」も記憶の対象に含めるため、ステップ 5 の後でもよい。ここでは計画書の順番を保ち、ステップ 5 でステップ 4 の記憶の対象に未対応キーを加える。

## 1. 共通のユーザーストーリー

- 海外のパッケージの作者として、英語の画面でツールを使いたい
- パッケージの作者として、プレビュー版の公開や、ライセンスの準備、複数のパッケージの編集を、このツールだけで済ませたい
- 既存の package.json を編集する利用者として、このツールが知らない項目を消されたくない

## 2. ステップ別の要求と受け入れ条件

### ステップ 1：英語・日本語の切り替え（#7）

今は画面のラベル・入力エラー・操作結果・確認ダイアログ・Console のメッセージが、すべて日本語の固定文字列になっている。これを英語と日本語で切り替えられるようにする。

- [ ] ウィンドウの上部に言語の選択（`English` / `日本語`）がある
- [ ] 言語を切り替えると、すぐに次のすべてがその言語で表示される：画面のラベル・見出し・ボタン、入力エラー、操作結果、上書きの確認ダイアログ、Console のエラーと警告、外部パッケージのポップアップの先頭項目、対応 Unity バージョンの「一覧外」
- [ ] 切り替えたときに表示中だった入力エラーと操作結果は消える（言語が混ざらないようにするため）。入力内容は変わらない
- [ ] ライセンスの選択肢（`MIT`、`Apache_2_0` など）は、どちらの言語でも英語の名前のまま
- [ ] 言語を一度も選んでいない状態で初めて開くと、PC の言語（`Application.systemLanguage`）が日本語なら日本語、それ以外なら英語になる
- [ ] 選んだ言語は EditorPrefs に保存され、Unity を再起動しても次回はその言語で開く
- [ ] 既存の EditMode テストが、どちらの言語の設定でも成功する。すべての文言が両方の言語に登録されていることを確かめるテストがある

### ステップ 2：プレビュー版のバージョン（#8）

UPM は `1.2.0-preview.1`、`1.2.0-exp.3`、`1.2.0-pre.2` のような、後ろにプレリリースの表記が付いたバージョンを受け付ける。自分のパッケージの `version` と、依存パッケージのバージョンの両方で扱えるようにする。

- [ ] パッケージのバージョンの Patch の後ろに、プレリリースの表記の入力欄がある。空なら今と同じ `X.Y.Z`、入力すると `X.Y.Z-<表記>` で出力される
- [ ] 依存パッケージの各行にも同じ入力欄があり、同じ形式で出力される
- [ ] 表記は SemVer のプレリリースの規則（英数字とハイフンを `.` で区切る。例 `preview.1`）に合わないと、入力エラーになる
- [ ] `1.2.3-preview.1` を持つ package.json を Load すると、本体・依存パッケージとも表記まで読み込まれ、警告は出ない（今は表記を読み捨てて警告している）
- [ ] 外部パッケージのポップアップでプレビュー版の登録済みパッケージ（例 `1.0.0-pre.3`）を選ぶと、表記まで入る
- [ ] ビルドメタデータ（`1.2.3+build.5` の `+` 以降）は対象外。Load したときは読み捨てて警告を出す

### ステップ 3：ライセンス None と LICENSE.md の作成（#9）

- [ ] ライセンスの選択肢に `None` が加わり、選ぶと `"license": "UNLICENSED"` が出力される（「誰にも使用を許可しない」を表す npm の慣習の値）
- [ ] `"license": "UNLICENSED"` を Load すると `None` が選ばれる
- [ ] 既存の選択肢の並びと値は変わらない（`None` は末尾に加える）
- [ ] `Proprietary` を選んでいるときだけ、「LICENSE.md を作成」ボタンが表示される
- [ ] ボタンを押すと、フォルダーパスのフォルダに、著者名と今年の年を入れた英語の独自ライセンスのひな形 `LICENSE.md` が作られる。既にファイルがあれば上書きの確認ダイアログが出る
- [ ] 著者名が空、またはフォルダが無いときは、作らずにエラーを表示する

### ステップ 4：読み込んだパッケージの記憶（#10）

複数のパッケージを行き来して編集できるように、パッケージごとの入力内容を Unity Editor を閉じるまで覚えておく。

- [ ] Load または Create に成功すると、そのパッケージ（フォルダーパスで区別する）が「記憶したパッケージ」の一覧に加わる
- [ ] 一覧から別のパッケージを選ぶと、今の入力内容（保存前の編集を含む）がそのパッケージの分として記憶されてから、選んだパッケージの入力内容とフォルダーパスに切り替わる
- [ ] 一覧から外すボタンがある
- [ ] ウィンドウを閉じて開き直しても、一覧と各パッケージの入力内容は残る
- [ ] Unity Editor を閉じると、一覧は消える（SessionState に保存する）

### ステップ 5：未対応キーの保持と JSON プレビュー（#11）

- [ ] Load した package.json の、このツールが扱わないキー（例 `type`、`repository`、`category`）が保持され、Create したときに値を変えずに出力される
- [ ] 保持した未対応キーは、ドメインリロードとステップ 4 の記憶でも消えない
- [ ] 画面に、保持している未対応キーの名前の一覧が表示される（無ければ表示しない）。一覧を消すボタンがある
- [ ] ファイル操作の欄に「JSON プレビュー」の折りたたみがあり、開くと Create したときに出力される内容が表示される。入力を変えると表示も変わる

### ステップ 6：現在の Unity の反映と Create 前の確認（#12）

- [ ] 対応 Unity バージョンの近くに「現在の Editor に合わせる」ボタンがあり、押すと今の Editor のバージョン（例 `6000.3.26f1`）から `unity` に `6000.3`、`unityRelease` に `26f1` が入る
- [ ] Create の前に次を確かめ、当てはまれば警告を出す（作成は止めない。警告の件数は操作結果に表示される）
  - サンプルのパスのフォルダが、フォルダーパスのフォルダの中に無い（`Samples~` を `Samples` に読み替えた場所にあれば警告しない）
  - `unityRelease` が空でなく、`0f1`・`26f1`・`0b5` のような形式（数字・英字 1 字・数字）に合わない

## 3. 共通の制約事項

- 編集するのは `src/PackageJsonGenerator/Assets/@MAH/PackageJson Generator/` とテスト（`Assets/@MAH/Tests/Editor/`）だけ。配布フォルダへはステップごとに同期する
- 新しいファイルには新しい GUID の `.meta` を付ける。既存の GUID は変えない
- パッケージの依存を増やさない（Unity Localization パッケージは使わない）。Unity 6000.0 に無い API を使わない
- パッケージ外の `Assets/@MAH/Editor/Utility/LanguageUtility.cs` は参照しない
- 検証・変換を変えたら EditMode テストも追加・修正する
- 新しい文言は、ステップ 1 で作る表に英語・日本語の両方で登録する
- メニューのパスとウィンドウのタイトルは変えない

## 4. スコープ外（今回やらないこと）

- 英語・日本語以外の言語。Unity Editor 自体の言語設定に合わせること（公開 API が無い）
- 言語を切り替えたときに、表示中の入力エラーや操作結果を新しい言語で表示し直すこと
- ビルドメタデータ（`+build`）の入力
- `Proprietary` 以外のライセンス（MIT など）の LICENSE.md の作成、ライセンス文の法的な正しさの保証
- 記憶したパッケージを Unity Editor の再起動後まで残すこと
- 未対応キーの値を画面で編集すること
- サンプルのフォルダが無いときに自動で作ること
- README の画像（`Image/`）の撮り直し
